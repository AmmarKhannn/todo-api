# Todo API

API Programming assignment — Ammar Khan

This is a Node.js API built with Express. It manages todos with three states: `todo`, `doing` and `done`. The data is kept in an array, so restarting the server clears it.

## Run the project

Install Node.js 22 or newer, then open this folder in VS Code. Open **Terminal → New Terminal** and run:

```bash
npm ci
npm start
```

The API runs at `http://localhost:3000`. Keep the terminal open while testing. Press Ctrl+C to stop it. You can change the port with the `PORT` environment variable.

## Endpoints

| Method | URL | Result |
| --- | --- | --- |
| POST | `/todos` | Creates a todo and returns 201, the object and a Location header |
| GET | `/todos` | Returns all todos with 200 |
| GET | `/todos?state=doing` | Returns todos matching the state with 200 |
| GET | `/todos/:id` | Returns one todo with 200 |
| PUT | `/todos/:id` | Updates supplied fields and returns the full object with 200 |
| DELETE | `/todos/:id` | Deletes a todo and returns 204 with no body |

All three states work as filters. An empty list returns `[]` with 200. PUT accepts partial updates, following the assignment's `{ "state": "doing" }` example. Fields that are left out keep their old values.

## Data and validation

| Field | Rules |
| --- | --- |
| `id` | UUID generated by the server; cannot be set or changed by the client |
| `title` | Required when creating; must be a string with some text; outside spaces are removed |
| `description` | Optional string; defaults to an empty string |
| `state` | Must be `todo`, `doing` or `done`; defaults to `todo` when creating |
| `dueDate` | Optional real calendar date in `YYYY-MM-DD` format, such as `2027-01-15` |
| `createdAt` | ISO timestamp set by the server; stays the same on update |
| `updatedAt` | ISO timestamp set by the server on create and update |

Unknown fields, including client-supplied IDs and timestamps, are rejected. Optional fields may be omitted, but `null` is not accepted. An update must include at least one editable field. Bodies must be JSON objects, not arrays or single values. The maximum body size is 16 KB.

POST and PUT need `Content-Type: application/json`. Responses with a body use JSON. The requests file also uses `Accept: application/json`.

## Examples

Create:

```http
POST http://localhost:3000/todos
Content-Type: application/json

{
  "title": "Write API documentation",
  "description": "OpenAPI + README examples",
  "state": "todo"
}
```

The response is 201 and contains the new todo, including its ID and timestamps. Copy the returned ID when making the requests below:

```http
GET http://localhost:3000/todos/RETURNED_ID
```

Update:

```http
PUT http://localhost:3000/todos/RETURNED_ID
Content-Type: application/json

{"state": "doing"}
```

Delete:

```http
DELETE http://localhost:3000/todos/RETURNED_ID
```

## Test in VS Code

1. Install **REST Client** by Huachao Mao.
2. Start the server with `npm start`.
3. Open `requests.rest` and click **Send Request** above request 1 first.
4. Run the remaining requests in order. Each heading gives the expected status.
5. Run the DELETE requests at the end, after testing the errors.

The header variables `@baseUrl` and `@json` avoid typing the same values again. The `@todoId` variable takes the ID from the named `createTodo` response. No Webex token is needed for this local API.

If a request says that `createTodo` has not been sent, run request 1 again. After restarting the server, also run request 1 again because the old ID no longer exists. The oversized-body requests read `test/large-body.json`; keep that file in its folder.

For an empty-list test, restart the server and send GET `/todos` before creating anything. It should return 200 and `[]`. GET `/todos?state=done` should also return an empty list at that point.

## Error responses and test cases

Errors return an object such as:

```json
{"error": "Title is required."}
```

| Code | Cases checked |
| --- | --- |
| 400 | Missing, empty, whitespace-only, non-string or null title |
| 400 | Non-string or null description |
| 400 | Unknown, uppercase, null or non-string state |
| 400 | Wrong date format, impossible date, non-string date or null date |
| 400 | Array, null, string, number or boolean body; missing body; malformed JSON |
| 400 | Empty update; unknown field; client-supplied ID or timestamps |
| 400 | Invalid, empty or repeated state filter; unknown query parameter |
| 400 | Invalid URL encoding |
| 404 | GET, PUT or DELETE for a missing todo; unknown endpoint; GET after deletion |
| 413 | JSON body larger than 16 KB |
| 415 | Missing or wrong Content-Type; unsupported charset or encoding |

The server also has a JSON 500 fallback for unexpected internal errors. This is not a client error.

## Automated test report

Run:

```bash
npm test
```

The tests send real HTTP requests to a local server on a free port. They check the full create/read/update/delete flow, all state filters, defaults, unique IDs, date handling, timestamps, Location and JSON headers, and the error cases above. Rejected updates are checked to make sure they do not change the stored todo.

Result from the development check on 5 November 2026, using Node.js 24.22.1: **76 tests passed, 0 failed**. The full output is in `test-results.txt`.

## Report and reflection

The working API covers all five required endpoints. The state-only update returns the whole todo, and deleting an item removes only that item from the array. Input checks run before changing the data.

One important part was handling bad input instead of only testing correct requests. For example, a date can look right but still be impossible, and a state must match one of the three allowed values. Saving requests in one REST Client file makes it easier to repeat these checks.

Using an array keeps this project simple, but it means the data is lost when the server stops. A database would be the next improvement if the API needed to keep real tasks.
